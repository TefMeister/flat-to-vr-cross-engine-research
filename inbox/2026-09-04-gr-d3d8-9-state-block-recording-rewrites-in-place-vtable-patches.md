# D3D8/D3D9: recording a state block rewrites the device's method table — an in-place vtable patch on a state-setting method dies the first time anyone calls `BeginStateBlock`/`EndStateBlock`

Filed by: `/gr`, 2026-09-04 (found on `enslaved-vr`; engine-agnostic, D3D runtime behaviour)
Source topic: `enslaved-vr/external-research/topics/2026-09-04-a-recorded-state-block-rewrites-the-device-vtable-and-kills-an-in-place-patch.md`

- **The behaviour:** `IDirect3DDevice9::BeginStateBlock` puts the runtime in recording mode by swapping the state-setting methods (`SetRenderState`, `SetTexture`, `SetVertexShaderConstantF`, …) in the device's method table; `EndStateBlock` writes the runtime's **own originals** back. Any third-party pointer written into those slots is overwritten. Methods that are not state-setting (`Present`, `Reset`, `CreateDevice`) are untouched — so a proxy sees *some* hooks survive and *some* vanish, permanently, with no error. Two independent witnesses, D3D8 and D3D9: gho (DxWnd, 2014-06) — *"BeginStateBlock recover all COM method pointers invalidating the hook patching. It's sufficient to hook this method to restore back the DxWnd routines"*; Paul Roussin (MS DirectX newsgroup, D3D8) — *"BeginStateblock will reset the device table so you have to … reset your modified addresses."* `[reported]`
- **When it bites:** whenever another resident of the process records a state block *after* the proxy patched — overlays (Steam, driver), `ID3DXSprite`/`ID3DXFont`, engines that use state blocks — typically on device reset/recovery, which is why it presents as "my hooks died after Reset". Enslaved's log matches it exactly (`Present`/`Reset` alive, slot 94 dead after every reset), pending instrumentation. `[hypothesis]` for that project.
- **Estate exposure:** every proxy that patches a D3D8/D3D9 device vtable in place — `enslaved-vr` (`proxy-d3d9`), `manhunt-2003-vr` (`proxy-d3d8`), `XIII2003-vr` (its `*_hook.cpp`) by a grep for `VirtualProtect` `[inferred-static 2026-09-04]`. Proxies that wrap the device object (own vtable) are immune by construction.
- **Playbook-shaped remedy, cheapest first:** (1) verify each patched slot every `Present` and log the first mismatch and its new value; (2) hook `BeginStateBlock`/`EndStateBlock` and re-apply patches after `EndStateBlock` (what DxWnd shipped); (3) prefer a code hook (MinHook) on the runtime function body over a vtable write for any state-setting method — immune to table rewrites; (4) full device wrapper when more than a few methods are needed.

Suggested library change: a short entry under the D3D9 (and D3D8) proxy plumbing / "hooks that silently die" material, cross-linked from the per-engine pages of the three exposed projects. The Enslaved run that confirms or refutes it for that game is queued as `[PD]` instrumentation + one `[FLAT]` launch.
